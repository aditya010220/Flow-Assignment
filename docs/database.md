# FlowLens — Database and Storage Design

## 1. Persistence responsibilities

FlowLens uses two storage systems for different data types:

- **Neon PostgreSQL:** structured application data, scan lifecycle, page records, evaluation results, findings and evidence metadata.
- **Cloudflare R2:** binary artifacts such as screenshots and optional recordings.

Do not store large screenshot/video binaries directly in PostgreSQL. Store object keys and metadata in the database.

## 2. Main entities

- `scans`: one submitted website inspection.
- `scan_pages`: pages visited during a scan.
- `evaluations`: one evaluation result per assignment-defined category.
- `findings`: individual observations and recommendations.
- `evidence`: metadata for screenshots and other captured artifacts.
- `scan_events`: optional audit/progress events for troubleshooting.

See [schema.md](./schema.md) for the proposed SQL schema.

## 3. Data lifecycle

1. Insert a scan with status `queued`.
2. Update it to `running` when a worker claims the job.
3. Insert page and evidence metadata as work completes.
4. Upload each binary artifact to R2 and persist its object key.
5. Persist evaluation results and findings.
6. Update the scan to `completed`.
7. If processing fails, update the scan to `failed` and persist a safe error code/message.

Use database transactions for related structured writes. Do not hold a database transaction open while Chromium is navigating a website or uploading large files.

## 4. R2 object-key convention

Recommended object keys:

```text
scans/{scanId}/pages/{pageId}/screenshots/{timestamp}.png
scans/{scanId}/pages/{pageId}/recordings/{timestamp}.webm
scans/{scanId}/exports/{filename}
```

Object keys should be generated by the backend/worker, not accepted blindly from the user.

## 5. Access and security

- Keep Neon credentials and R2 access keys server-side.
- Use a least-privilege R2 token scoped to the required bucket.
- Use short-lived signed URLs or an authenticated backend proxy for private evidence.
- Validate that requested evidence belongs to the requested scan.
- Define retention and cleanup behavior for abandoned/failed scans.
- Never log credentials or signed URLs.
- Apply database connection pooling suitable for serverless PostgreSQL.

## 6. Environment variables

Example `.env.example`:

```dotenv
NODE_ENV=development
PORT=5000
DATABASE_URL=
R2_ACCOUNT_ID=
R2_ACCESS_KEY_ID=
R2_SECRET_ACCESS_KEY=
R2_BUCKET_NAME=
R2_ENDPOINT=
R2_PUBLIC_BASE_URL=
WORKER_CALLBACK_SECRET=
SCAN_MAX_PAGES=5
SCAN_TIMEOUT_MS=180000
```

Only include variables actually used by the implementation. Do not commit `.env`.

## 7. Migration strategy

- Keep SQL migrations in `backend/migrations/`.
- Version every schema change.
- Apply migrations in development and deployment.
- Avoid manually changing production tables without a migration.
- Test migrations against a disposable database before applying them to shared data.

## 8. Operational checks

- Confirm database connectivity at backend startup.
- Add indexes for scan listing and foreign-key lookups.
- Monitor connection limits.
- Verify R2 upload and retrieval independently.
- Ensure failed uploads do not produce database rows that appear to reference valid evidence.
